# 0006: No OTLP receiver in v1

- **Status:** accepted (P5-05, 2026-10-25)
- **Evidence:** [docs/spikes/otlp.md](../spikes/otlp.md)

## Context

Claude Code, Gemini CLI and Codex can all export OpenTelemetry. One OTLP/HTTP endpoint (`/v1/logs`) could be a
generic path that needs no adapter or hook shim per provider. The spike captured real telemetry from Codex 0.164.0
and Gemini CLI 0.65.0 (Claude Code needs a signed-in session, so it wasn't captured).

## Decision

Don't ship an OTLP receiver in v1. The hook shims and file adapters stay the way providers report. Custom agents
use the SDKs (`sdk/`).

The reasons, all measured:

1. **It can't run the status machine.** Neither CLI reports a turn end or a session end, Gemini has no tool start,
   and no telemetry says "waiting for you". Agents would stay "working" until a timeout.
2. **It can't place agents.** Neither carries the working folder, so every agent would land in "(no project)".
3. **It sends content we must not need.** Codex includes tool arguments and output, and Gemini includes system
   instructions on every request. The hook shims drop such content before it leaves the agent's process; with OTLP it
   would already have left.
4. **It's heavy.** 205 KB (Codex) and 1.3 MB (Gemini) for a few seconds of work, against ~5 KB through the shims.
5. **It's intrusive to set up.** It means editing Codex's `config.toml` (which we never touch) or Gemini's telemetry
   settings, and it competes with any telemetry pipeline the user already runs.

## Consequences

- No `/v1/logs` route. The edge guard and ingest stay as they are.
- The spike's tools stay in `docs/spikes/otlp/` to re-measure later.
- Revisit if the CLIs start exporting lifecycle events (turn and session end), the working folder, and a way to turn
  content off. Telemetry could then complement the shims, mainly for tokens and Gemini's PID.
